# Evaluation

The evaluation answers one narrow question: given the same candidate places, what does each part of the pipeline change, and does the gate ever let a place through that breaks a requirement?

Current results are in [EVALUATION_RESULTS.md](EVALUATION_RESULTS.md). They are regenerated by `npm run eval`.

## Design

Each scenario opens a case, records one disruption, resolves any ambiguous signals using a stated choice, and runs one search. Four lists are then compared.

1. **Ungated list.** The top three places by provider rank with no feasibility gate. It stands for a plain recommender. The original venue is left out, as any sensible recommender would.
2. **Taste Off.** Gated places ordered by distance, then price, then name.
3. **Popular.** Gated places ordered by the provider's general popularity, most popular first, with distance and price as tie breakers. It uses none of the group's signals, so it stands for a plain list of well known places.
4. **Taste On.** Gated places ordered by the recovery score. The venue that fell through counts as a taste signal unless the scenario turns it off.

All gated arms use the identical pool, gate and exclusions. The report states whether the eligible sets were identical in every scenario.

## Measures

- How often the ungated top three contained a place that breaks a hard requirement.
- Violations in the gated top three, judged by an independent oracle. The oracle is a separate implementation of the constraint rules that reads raw venue facts, so it can disagree with the gate and would reveal a bug.
- Whether the top choice differs between Taste On and Taste Off, and between Taste On and Popular.
- Overlap of the top three, and Kendall tau between the full orderings.
- Mean provider affinity of the top three in each arm, reported separately from the recovery score.
- For scenarios with no eligible place, whether a way forward was offered.

## What the offline run can show

It shows that the gate rules out places that break requirements, that the oracle agrees with the gate, that Taste On and Taste Off differ in ordering and not in eligibility, and that the no option case is handled without guessing.

## What it cannot show

- It cannot show that Qloo predicts what real people enjoy. The catalogue, the venues and the affinity are invented and hand authored.
- The mean affinity difference is not independent evidence of better taste, because the simulated affinity defines taste in that catalogue.
- The share of scenarios where an ungated list breaks a requirement depends on how the catalogue and scenarios were written. It is not a rate in the real world.
- No people were involved. Nothing here measures satisfaction, trust or outcomes.

## Live evaluation

`npm run eval -- --live scenarios.json` runs the same comparison against Qloo for scenarios you supply, validated by the same schema as the intake form. It needs `QLOO_API_KEY`.

The preregistered run is `npm run eval:live`, over the frozen scenarios in `evaluation/live-scenarios.json`. Its design and twelve numeric predictions were committed in [PREREGISTRATION.md](PREREGISTRATION.md) before any scenario was ranked, and its registered results are in [EVALUATION_LIVE.md](EVALUATION_LIVE.md), rendered from `results/live-qloo.json`. The first run exposed two product defects, which were fixed and recorded as a dated amendment, and a second run on the same scenarios, predictions, thresholds and seed is in [EVALUATION_LIVE_SECOND_RUN.md](EVALUATION_LIVE_SECOND_RUN.md). It is not independent of the first. Both runs met 9 of the 12 predictions and missed the same three. [EVALUATION_LIVE_NOTES.md](EVALUATION_LIVE_NOTES.md) explains every miss and records what a read only look at the pools found. The live run does not use the OpenStreetMap lookup. The gate and the independent oracle both work from the facts Qloo returned, so a fact Qloo does not state is unknown to both.

## Baseline comparison

The question that the live evaluation did not ask is whether AFTERGLOW beats simpler ways of choosing a replacement. `npm run eval:baselines` ranks each plan five ways from the same Qloo pool (random, nearest first, popular, Qloo taste alone, and AFTERGLOW), each with and without the gate, and judges every list with the independent oracle. The 20 scenarios of `evaluation/live-scenarios.json` are the development set, and the 20 scenarios of `evaluation/test-scenarios.json`, in five other cities, are the test set. The design, statistics and 14 predictions were registered in [PREREGISTRATION_V2.md](PREREGISTRATION_V2.md) before the test set was ranked, and its thresholds follow one rule from the development results. The results are in [EVALUATION_BASELINES_TEST.md](EVALUATION_BASELINES_TEST.md) and the development results in [EVALUATION_BASELINES_DEV.md](EVALUATION_BASELINES_DEV.md). Thirteen predictions were met and one was missed, as explained in [EVALUATION_BASELINES_NOTES.md](EVALUATION_BASELINES_NOTES.md). A language model without Qloo data is not among the baselines.

## Reproducing

```sh
npm ci
npm run eval
```

The command is deterministic apart from the timestamp. It rewrites `data/evaluation/report-offline-simulated.json` and `docs/EVALUATION_RESULTS.md`.
