# Evaluation

The evaluation answers one narrow question: given the same candidate places, what does each part of the pipeline change, and does the gate ever let a place through that breaks a requirement?

Current results are in [EVALUATION_RESULTS.md](EVALUATION_RESULTS.md). They are regenerated by `npm run eval`.

## Design

Each scenario opens a case, records one disruption, resolves any ambiguous signals using a stated choice, and runs one search. Three lists are then compared.

1. **Ungated list.** The top three places by provider rank with no feasibility gate. It stands for a plain recommender. The original venue is left out, as any sensible recommender would.
2. **Taste Off.** Gated places ordered by distance, then price, then name.
3. **Taste On.** Gated places ordered by the recovery score.

Both gated arms use the identical pool, gate and exclusions. The report states whether the eligible sets were identical in every scenario.

## Measures

- How often the ungated top three contained a place that breaks a hard requirement.
- Violations in the gated top three, judged by an independent oracle. The oracle is a separate implementation of the constraint rules that reads raw venue facts, so it can disagree with the gate and would reveal a bug.
- Whether the top choice differs between Taste On and Taste Off.
- Overlap of the top three, and Kendall tau between the full orderings.
- Mean provider affinity of the top three in each arm, reported separately from the recovery score.
- For scenarios with no eligible place, whether a way forward was offered.

## What the offline run can show

It shows that the gate rules out places that break requirements, that the oracle agrees with the gate, that Taste On and Taste Off differ in ordering and not in eligibility, and that the no option case is handled without guessing.

## What it cannot show

- It cannot show that Qloo predicts what real people enjoy. The catalogue, the venues and the affinity are invented and hand authored.
- The mean affinity difference is not independent evidence of better taste, because the simulated affinity defines taste in that catalogue.
- The share of scenarios where an ungated list breaks a requirement depends on how the catalogue and scenarios were written. It is not a rate in the real world.
- No people were involved. Nothing here measures satisfaction, trust or outcomes.

## Live evaluation

`npm run eval -- --live scenarios.json` runs the same comparison against Qloo for scenarios you supply, validated by the same schema as the intake form. It needs `QLOO_API_KEY`. Live venues lack opening hours, dietary options, accessibility and capacity, so the oracle is switched off and violations are only those the gate can establish from facts the provider returned. The report says so. The live evaluation has not yet been run.

## Reproducing

```sh
npm ci
npm run eval
```

The command is deterministic apart from the timestamp. It rewrites `data/evaluation/report-offline-simulated.json` and `docs/EVALUATION_RESULTS.md`.
